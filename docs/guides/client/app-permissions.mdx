# App roles and permissions client

Wraps every endpoint from the [app permission guide](../app-permissions.mdx) into `appPermissionsApi`, built on the [`apiRequest`](./index.mdx) helper. Each action below has its own client example. The [authorization route reference](../../routes/authorization.mdx) describes the complete HTTP contract.

Application roles are separate from organization roles. Each account has one app role, with explicit permission keys. Assigning a role replaces the previous assignment; there are no direct user grants, wildcard keys, or inherited roles.

<Callout type="info" title="UI components">
  The examples follow the other client guides: React, TypeScript, and local [shadcn/ui](https://ui.shadcn.com) components. The dialog and select examples use the [Radix component APIs](https://ui.shadcn.com/docs/components/radix/dialog), including `asChild`. In an initialized shadcn project, install with `npx shadcn@latest add button input textarea card label alert dialog select table badge checkbox`.
</Callout>

## Before using the client

Both authorization modes are supported. Without `WithAppPermissions`, or with
`Enable: false`, accounts use the fixed `"admin"` and `"user"` roles and account
JSON includes `role`. The app permission endpoints are not mounted in that mode.
Enabling app permissions selects configurable app roles and explicit grants.

Enable the feature in your existing server configuration:

```go
goauth.WithAppPermissions(goauth.AppPermissionsConfig{
    Enable:               true,
    EnableManagementHTTP: true,
    DefaultRoleSlug:      "user",
})
```

Apply the canonical schema and initialize the protected administrator through trusted server setup before accepting accounts. Follow [Enable and initialize](../app-permissions.mdx#enable-and-initialize); initialization has no browser endpoint. Startup does not install library permissions.

`Enable: true` exposes `GET /auth/access`. The `/admin/authorization/*` routes also need `EnableManagementHTTP: true`. An unmounted route is not a permission denial and should not be treated as an empty list.

Sign in first using the [authentication client](./authentication.mdx). Custom operators use ordinary login, even when their roles contain library permissions. Protected administrators require email 2FA by default. Custom roles follow the non-admin policy: library actions require second-factor assurance when global or per-account 2FA requires it. On `two_factor_required`, complete a fresh login and its challenge before retrying. Reading access or refreshing a session does not add second-factor assurance.

The examples use `API_BASE = "/api"`, matching the same-origin proxy convention in the other guides. Replace it with your mounted prefix or configured backend origin. Keep cookies, CSRF handling, and origin configuration from [Setup](./index.mdx) and [Deployment](../deployment.mdx); never send an actor ID or session token in a permission body.

In enabled mode, account JSON omits `role`. Read `appRoleId` from the user and current access from `/auth/access`. If you use the [Auth Provider](./auth-provider.mdx), its user type must allow `role?: "admin" | "user"` for disabled mode and the enabled-mode fields `appRoleId?: string` and `appRoleAssignmentRevision?: number`. Organization membership still has its own `role`.

## The wrapper

The response types below mirror the wire format. Revisions are numbers from the response, not counters the browser invents. Management lists return arrays inside an envelope; create/update calls return a single object; deletes return `204` without a body.

```ts
// lib/api/app-permissions.ts
import { apiRequest } from "./client";

const API_BASE = "/api";
const ROOT = "/admin/authorization";

export interface AppPermission {
  id: string;
  key: string;
  name: string;
  description: string;
  isEnabled: boolean;
  isSystem: boolean;
  revision: number;
  createdAt: string;
  updatedAt: string;
}

export interface AppRole {
  id: string;
  slug: string;
  name: string;
  description: string;
  isEnabled: boolean;
  systemKey?: "platform_admin" | "user";
  revision: number;
  permissionKeys: string[];
  createdAt: string;
  updatedAt: string;
}

export interface LibraryPermission {
  key: string;
  name: string;
  description: string;
}

export interface AppUserRole {
  role: AppRole;
  assignmentRevision: number;
}

export interface AppAccess extends AppUserRole {
  isFullAccess: boolean;
  permissionKeys: string[];
  revision: number;
}

export interface LibraryUpdateResult {
  created: string[];
  deleted: string[];
  unchanged: string[];
}

export interface MetadataUpdate {
  expectedRevision: number;
  name?: string;
  description?: string;
  isEnabled?: boolean;
}

interface Page {
  limit?: number;
  offset?: number;
}

function pageQuery({ limit = 20, offset = 0 }: Page = {}) {
  return new URLSearchParams({ limit: String(limit), offset: String(offset) });
}

// Compatible with both the plain wrapper in Setup and its typed variant.
function request<T>(method: string, path: string, body?: unknown): Promise<T> {
  return apiRequest(API_BASE, method, path, body) as Promise<T>;
}

export const appPermissionsApi = {
  myAccess: () => request<AppAccess>("GET", "/auth/access"),

  libraryCatalog: () =>
    request<{ permissions: LibraryPermission[] }>("GET", `${ROOT}/library-permissions`),

  updateLibrary: (input: { create: string[]; delete: string[] }) =>
    request<LibraryUpdateResult>("PATCH", `${ROOT}/library-permissions`, input),

  listPermissions: (page: Page = {}) =>
    request<{ permissions: AppPermission[] }>("GET", `${ROOT}/permissions?${pageQuery(page)}`),

  createPermission: (input: { key: string; name: string; description?: string }) =>
    request<AppPermission>("POST", `${ROOT}/permissions`, input),

  updatePermission: (permissionId: string, input: MetadataUpdate) =>
    request<AppPermission>("PATCH", `${ROOT}/permissions/${encodeURIComponent(permissionId)}`, input),

  deletePermission: (permissionId: string, expectedRevision: number) =>
    request<void>("DELETE", `${ROOT}/permissions/${encodeURIComponent(permissionId)}?${new URLSearchParams({ expectedRevision: String(expectedRevision) })}`),

  listRoles: (page: Page = {}) =>
    request<{ roles: AppRole[] }>("GET", `${ROOT}/roles?${pageQuery(page)}`),

  createRole: (input: { slug: string; name: string; description?: string; permissionKeys: string[] }) =>
    request<AppRole>("POST", `${ROOT}/roles`, input),

  updateRole: (roleId: string, input: MetadataUpdate) =>
    request<AppRole>("PATCH", `${ROOT}/roles/${encodeURIComponent(roleId)}`, input),

  setRolePermissions: (roleId: string, input: { expectedRevision: number; permissionKeys: string[] }) =>
    request<AppRole>("PUT", `${ROOT}/roles/${encodeURIComponent(roleId)}/permissions`, input),

  deleteRole: (roleId: string, expectedRevision: number) =>
    request<void>("DELETE", `${ROOT}/roles/${encodeURIComponent(roleId)}?${new URLSearchParams({ expectedRevision: String(expectedRevision) })}`),

  getUserRole: (userId: string) =>
    request<AppUserRole>("GET", `${ROOT}/users/${encodeURIComponent(userId)}/role`),

  getUserAccess: (userId: string) =>
    request<AppAccess>("GET", `${ROOT}/users/${encodeURIComponent(userId)}/access`),

  setUserRole: (userId: string, input: {
    roleId: string;
    expectedRoleRevision: number;
    expectedAssignmentRevision: number;
  }) => request<AppUserRole>("PUT", `${ROOT}/users/${encodeURIComponent(userId)}/role`, input),
};

// Client conveniences, not additional server endpoints. Fetch every page for
// selectors; the default page of 20 is not the complete installed set.
export async function loadAllPermissions(): Promise<AppPermission[]> {
  const result: AppPermission[] = [];
  for (let offset = 0; ; offset += 100) {
    const { permissions } = await appPermissionsApi.listPermissions({ limit: 100, offset });
    result.push(...permissions);
    if (permissions.length < 100) return result;
  }
}

export async function loadAllRoles(): Promise<AppRole[]> {
  const result: AppRole[] = [];
  for (let offset = 0; ; offset += 100) {
    const { roles } = await appPermissionsApi.listRoles({ limit: 100, offset });
    result.push(...roles);
    if (roles.length < 100) return result;
  }
}

export async function reloadPermission(id: string): Promise<AppPermission> {
  const permission = (await loadAllPermissions()).find((item) => item.id === id);
  if (!permission) throw { error: "permission_not_found" };
  return permission;
}

export async function reloadRole(id: string): Promise<AppRole> {
  const role = (await loadAllRoles()).find((item) => item.id === id);
  if (!role) throw { error: "role_not_found" };
  return role;
}
```

IDs must be lowercase, hyphenated UUIDs exactly as returned by the API. URL encoding does not make an invalid UUID valid. Keys and slugs are immutable; metadata updates do not accept them. Management bodies are limited to 64 KiB and must contain one JSON object. Unknown management JSON fields, including `actor`, are rejected.

`loadAllPermissions` and `loadAllRoles` are appropriate for small management catalogs. There is no count endpoint, single-definition GET, or single-role GET in this surface. Lists sort by permission key or role slug, accept limits 1–100, and default to 20 (`0` also selects 20). Offsets must be nonnegative. A full page may have a following empty page. Separate page requests do not promise a single database snapshot: refresh selectors after mutations and handle stale revisions at submission.

### Which access each action needs

Protected admin can execute all known library actions, including uninstalled ones. Custom roles need the corresponding installed and enabled key, plus the delegation checks described with each mutation.

| Wrapper method | Required access |
|---|---|
| `myAccess` | Authenticated account with an enabled app role |
| `libraryCatalog`, `updateLibrary` | Protected administrator; these cannot be delegated |
| `listPermissions` | `goauth.app.permissions.read` |
| `createPermission` | `goauth.app.permissions.create` |
| `updatePermission` | `goauth.app.permissions.update` |
| `deletePermission` | `goauth.app.permissions.delete` |
| `listRoles`, `getUserRole`, `getUserAccess` | `goauth.app.roles.read` |
| `createRole` | `goauth.app.roles.create` |
| `updateRole`, `setRolePermissions` | `goauth.app.roles.update` |
| `deleteRole` | `goauth.app.roles.delete` |
| `setUserRole` | `goauth.app.roles.assign` |

The examples that load a permission picker additionally need `goauth.app.permissions.read`; role selectors and reload buttons need `goauth.app.roles.read`. A write grant alone does not grant the reads used by a richer UI. You can pass previously loaded records to a simpler mutation component when the operator does not have list access.

## Error handling

Use the stable code to decide what to do. The helper supports the plain `{error,message}` thrown by [Setup](./index.mdx), the authentication guide's `AuthError.code` variant, and network `Error` objects.

```ts
// lib/app-permission-errors.ts
export function permissionErrorCode(error: unknown): string | undefined {
  if (typeof error !== "object" || error === null) return undefined;
  const value = error as { error?: unknown; code?: unknown };
  if (typeof value.error === "string") return value.error;
  return typeof value.code === "string" ? value.code : undefined;
}

const messages: Record<string, string> = {
  forbidden: "You no longer have access, or this change exceeds your delegation rights.",
  two_factor_required: "Sign in again and complete the two-factor challenge before retrying.",
  authorization_conflict: "This record changed. Reload it, review the changes, and submit again.",
  permission_exists: "That permission key already exists.",
  permission_not_found: "The permission is missing or unavailable for granting.",
  permission_in_use: "Remove this key from every role before deleting the definition.",
  role_exists: "That role slug already exists.",
  role_not_found: "The role is missing or unavailable.",
  role_in_use: "This role is assigned to accounts or configured as the default.",
  protected_role: "Built-in roles cannot be edited, disabled, or deleted.",
  protected_permission: "Use library provisioning to install or remove library definitions.",
  unknown_library_permission: "Use a supported key from the library catalog.",
  invalid_permission_key: "Use a lowercase dot-separated permission key, such as app.posts.delete.",
  last_admin: "Keep at least one usable protected administrator.",
  user_not_found: "The selected account no longer exists.",
  app_permissions_disabled: "Application permissions are not available on this server.",
  app_permissions_not_initialized: "A server administrator must initialize application permissions.",
};

export function getPermissionErrorMessage(error: unknown): string {
  const code = permissionErrorCode(error);
  if (code && messages[code]) return messages[code];
  if (typeof error === "object" && error !== null && "message" in error &&
      typeof error.message === "string") return error.message;
  return "Could not complete the request. Check your connection and try again.";
}
```

`authorization_conflict` is a `409`, not a signal to increment a revision locally or retry automatically. Reload the affected record and let the operator review it. Permission edits/deletes use the definition revision; role edits/grant replacements/deletes use the role revision; assignment needs both the selected role revision and target assignment revision. The global `AppAccess.revision` is informational and is never an `expectedRevision` value.

On `401` or `user_banned`, let the shared wrapper clear authentication state. Do not sign out on every `403`: it may be an ordinary permission denial or an MFA requirement. After a denial, refresh current access and hide unavailable controls. A `429` from the shared wrapper includes `retryAfter` in seconds; display a retry delay rather than automatically looping a write. JSON validation and infrastructure errors are covered in [Error handling](../../error-handling.mdx#app-authorization).

A network failure can happen after a write committed. Reload the relevant definitions, role, or assignment before retrying; a failed browser request is not proof that the server rolled back. Create operations may already have produced the key or slug you submitted.

### Shared UI helpers

Copy these helpers once. The read hook ignores late responses after a reload or unmount and clears old data while loading. It does not poll or retry failed requests. Pass a stable function, using `useCallback` when it depends on a prop or page offset.

```tsx
// components/app-permission-ui.tsx
"use client";

import { useEffect, useId, useState } from "react";
import { Alert, AlertDescription } from "@/components/ui/alert";
import { Checkbox } from "@/components/ui/checkbox";
import { Label } from "@/components/ui/label";
import { Badge } from "@/components/ui/badge";
import type { AppAccess, AppPermission } from "../lib/api/app-permissions";
import { getPermissionErrorMessage } from "../lib/app-permission-errors";

export function usePermissionQuery<T>(load: () => Promise<T>) {
  const [version, setVersion] = useState(0);
  const [state, setState] = useState<{ data?: T; error: string | null; loading: boolean }>({
    error: null, loading: true,
  });

  useEffect(() => {
    let active = true;
    setState({ error: null, loading: true });
    load().then(
      (data) => { if (active) setState({ data, error: null, loading: false }); },
      (error: unknown) => {
        if (active) setState({ error: getPermissionErrorMessage(error), loading: false });
      },
    );
    return () => { active = false; };
  }, [load, version]);

  return { ...state, reload: () => setVersion((value) => value + 1) };
}

export function PermissionError({ message }: { message: string | null }) {
  if (!message) return null;
  return <Alert variant="destructive"><AlertDescription>{message}</AlertDescription></Alert>;
}

// Effective keys are authoritative for UI availability. Do not use
// isFullAccess to bypass an absent or disabled business definition.
export function hasPermission(access: AppAccess | null | undefined, key: string) {
  return access?.permissionKeys.includes(key) ?? false;
}

export function PermissionKeyPicker({ permissions, selected, onChange, access, disabled = false }: {
  permissions: AppPermission[];
  selected: string[];
  onChange: (keys: string[]) => void;
  access: AppAccess;
  disabled?: boolean;
}) {
  const id = useId();
  return (
    <div className="space-y-3">
      {permissions.length === 0 && <p className="text-sm text-muted-foreground">No definitions installed.</p>}
      {permissions.map((permission) => {
        const checked = selected.includes(permission.key);
        const canAdd = permission.isEnabled && (access.isFullAccess || hasPermission(access, permission.key));
        return (
          <div key={permission.id} className="flex items-start gap-3 rounded-md border p-3">
            <Checkbox
              id={`${id}-${permission.id}`}
              checked={checked}
              disabled={disabled || (!checked && !canAdd)}
              onCheckedChange={(value) => onChange(value === true
                ? [...selected, permission.key]
                : selected.filter((key) => key !== permission.key))}
            />
            <div className="space-y-1">
              <Label htmlFor={`${id}-${permission.id}`}>{permission.name}</Label>
              <p className="break-all text-sm text-muted-foreground">{permission.key}</p>
              {!permission.isEnabled && <Badge variant="secondary">Disabled</Badge>}
              {!access.isFullAccess && !hasPermission(access, permission.key) &&
                <p className="text-sm text-muted-foreground">Outside your current grants</p>}
            </div>
          </div>
        );
      })}
    </div>
  );
}
```

The picker lets an operator uncheck an existing disabled key. Keeping it in a replacement request fails because replacements accept only enabled definitions. A delegate must still hold **all existing and requested keys** to replace a role's grants, so removal of an unavailable existing key may require protected admin. The picker is a convenience; the server enforces that rule.

## Read your current access

`GET /auth/access` → `{role,isFullAccess,permissionKeys,assignmentRevision,revision}`.

Use the top-level effective `permissionKeys` to render actions. The nested `role.permissionKeys` in an access response is not the effective grant list. Protected admin includes every known library key and every currently enabled business key; a custom role includes its enabled installed grants. `isFullAccess` describes protected-admin identity, not a wildcard that enables disabled business actions.

### Access card

```tsx
// components/my-app-access.tsx
"use client";

import { Button } from "@/components/ui/button";
import { Card, CardContent, CardHeader, CardTitle } from "@/components/ui/card";
import { Badge } from "@/components/ui/badge";
import { appPermissionsApi } from "../lib/api/app-permissions";
import { PermissionError, usePermissionQuery } from "./app-permission-ui";

export function MyAppAccess() {
  const { data, error, loading, reload } = usePermissionQuery(appPermissionsApi.myAccess);
  return (
    <Card>
      <CardHeader><CardTitle>Your application access</CardTitle></CardHeader>
      <CardContent className="space-y-4">
        <PermissionError message={error} />
        {loading && <p>Loading access...</p>}
        {!loading && data && <>
          <p>{data.role.name} <Badge>{data.isFullAccess ? "Protected admin" : "Custom or baseline role"}</Badge></p>
          <p className="text-sm text-muted-foreground">Assignment {data.assignmentRevision} · App revision {data.revision}</p>
          {data.permissionKeys.length === 0 ? <p>No explicit permissions.</p> :

    </Card>

```

Mount this after authentication, and unmount or key it by the authenticated user's ID when that user changes. Clear cached access on logout. Refresh after local role/grant/definition changes, when returning to an administrative page, and after a permission denial. Other operators' changes do not produce a push notification. Existing sessions observe new grants on subsequent backend checks; refreshing this card updates the UI.

## Read the library catalog

`GET /admin/authorization/library-permissions` → `{permissions:[{key,name,description}]}`. Protected admin only.

The catalog contains supported `goauth.app.*` keys, whether installed or not. It has no IDs, revisions, `isEnabled`, or installation flag. Join it to the installed-definition list by `key` when you need installation status.

## Install library permissions

`PATCH /admin/authorization/library-permissions` with `{create:[keys],delete:[]}` → `{created,deleted,unchanged}`. Protected admin only.

Installing makes a definition available for custom-role grants. It does not grant that key to anyone. Each batch needs 1–100 total distinct supported keys; duplicates or create/delete overlap reject the entire batch. Installing an existing definition reports it in `unchanged`.

### Install form

```tsx
// components/install-library-permissions.tsx
"use client";

import { useId, useState } from "react";
import { Button } from "@/components/ui/button";
import { Card, CardContent, CardHeader, CardTitle } from "@/components/ui/card";
import { Checkbox } from "@/components/ui/checkbox";
import { Label } from "@/components/ui/label";
import { appPermissionsApi } from "../lib/api/app-permissions";
import { getPermissionErrorMessage } from "../lib/app-permission-errors";
import { PermissionError, usePermissionQuery } from "./app-permission-ui";

export function InstallLibraryPermissions({ onChanged }: { onChanged: () => void }) {
  const catalog = usePermissionQuery(appPermissionsApi.libraryCatalog);
  const [selected, setSelected] = useState<string[]>([]);
  const [error, setError] = useState<string | null>(null);
  const [result, setResult] = useState<string | null>(null);
  const [loading, setLoading] = useState(false);
  const id = useId();

  async function install() {
    setLoading(true); setError(null); setResult(null);
    try {
      const response = await appPermissionsApi.updateLibrary({ create: selected, delete: [] });
      setResult(`Installed ${response.created.length}; already installed ${response.unchanged.length}.`);
      setSelected([]);
      onChanged();
    } catch (error: unknown) { setError(getPermissionErrorMessage(error)); }
    finally { setLoading(false); }
  }

  return (
    <Card>
      <CardHeader><CardTitle>Install library permissions</CardTitle></CardHeader>
      <CardContent className="space-y-4">
        <PermissionError message={error ?? catalog.error} />
        {catalog.loading && <p>Loading catalog...</p>}
        {catalog.data?.permissions.map((permission) =>
          <div key={permission.key} className="flex items-center gap-2">
            <Checkbox id={`${id}-${permission.key}`} checked={selected.includes(permission.key)} disabled={loading}
              onCheckedChange={(checked) => setSelected((keys) => checked === true ? [...keys, permission.key] : keys.filter((key) => key !== permission.key))} />
            <Label htmlFor={`${id}-${permission.key}`}>{permission.name} · {permission.key}</Label>
          </div>,
        )}
        {result && <p role="status">{result}</p>}
        <Button disabled={loading || catalog.loading || !!catalog.error || selected.length === 0 || selected.length > 100} onClick={install}>
          {loading ? "Installing..." : `Install ${selected.length} selected`}
        </Button>
        <Button variant="outline" disabled={loading || catalog.loading} onClick={catalog.reload}>Reload catalog</Button>
      </CardContent>
    </Card>
  );
}
```

Use `onChanged` to refresh installed definitions and role pickers. Follow installation with [role creation](#create-a-custom-role) or [grant replacement](#replace-a-roles-permissions).

## Remove library permissions

`PATCH /admin/authorization/library-permissions` with `{create:[],delete:[keys]}`. Protected admin only.

Removal deletes every role link to the selected definitions in the same transaction, bumps affected role revisions, and changes subsequent authorization checks. Protected admin retains the known library action. Reinstalling creates a new definition and **does not restore grants**. Removing an absent key reports `unchanged`.

### Removal confirmation

```tsx
// components/remove-library-permission.tsx
"use client";

import { useState } from "react";
import { Button } from "@/components/ui/button";
import { Dialog, DialogContent, DialogDescription, DialogFooter, DialogHeader, DialogTitle, DialogTrigger } from "@/components/ui/dialog";
import { appPermissionsApi, type AppPermission } from "../lib/api/app-permissions";
import { getPermissionErrorMessage } from "../lib/app-permission-errors";
import { PermissionError } from "./app-permission-ui";

export function RemoveLibraryPermission({ permission, onRemoved }: {
  permission: AppPermission; onRemoved: () => void;
}) {
  const [open, setOpen] = useState(false);
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState<string | null>(null);

  async function remove() {
    setLoading(true); setError(null);
    try {
      await appPermissionsApi.updateLibrary({ create: [], delete: [permission.key] });
      setOpen(false); onRemoved();
    } catch (error: unknown) { setError(getPermissionErrorMessage(error)); }
    finally { setLoading(false); }
  }

  return (
    <Dialog open={open} onOpenChange={(next) => { if (!loading) { setOpen(next); setError(null); } }}>
      <DialogTrigger asChild><Button variant="destructive" disabled={!permission.isSystem}>Remove library definition</Button></DialogTrigger>
      <DialogContent>
        <DialogHeader>
          <DialogTitle>Remove {permission.key}?</DialogTitle>
          <DialogDescription>All custom-role grants for this action will be removed. Reinstalling will not restore them.</DialogDescription>
        </DialogHeader>
        <PermissionError message={error} />
        <DialogFooter>
          <Button variant="outline" disabled={loading} onClick={() => setOpen(false)}>Cancel</Button>
          <Button variant="destructive" disabled={loading} onClick={remove}>{loading ? "Removing..." : "Remove definition and grants"}</Button>
        </DialogFooter>
      </DialogContent>
    </Dialog>
  );
}
```

Pass an `isSystem` row from the installed-definition list. After removal, reload definitions, roles, assignments being edited, and current access. There is no `expectedRevision` in this protected catalog request; it is an atomic key-based provisioning operation.

### Mixed install/remove batch

For a reviewed change that must install and remove together, use the same endpoint once. This separate example accepts a parent-reviewed plan; it displays both sets and lets the server reject an unsupported catalog key. A network failure can leave the outcome unknown, so reload installed state before deciding whether to retry. If the current state already matches the batch, repeating it reports the keys in `unchanged` without changing revisions. Review the state first because another administrator may have changed it meanwhile.

## Create a business permission

`POST /admin/authorization/permissions` with `{key,name,description}` → a definition, `201`. Requires `goauth.app.permissions.create`.

## Update, disable, or enable a business permission

`PATCH /admin/authorization/permissions/{permissionID}` with `{expectedRevision,name?,description?,isEnabled?}` → the updated definition, `200`. Requires `goauth.app.permissions.update`.

Omitting an optional field preserves it; `description: ""` clears the description, and `isEnabled: false` disables the key. Use the revision of the definition being edited. A delegate must also currently hold that business key. Once it is disabled, the delegate cannot re-enable it to regain access; protected admin can.

Disabled business definitions deny everyone, including protected admin, on subsequent checks. Disabling keeps role links; re-enabling makes those existing grants effective again. This differs from library removal, which deletes links.

```tsx
    </CardContent>
  </Card>;
}
```

Use a parent key of `role.id + ":" + role.revision` when changing the selected snapshot. The server knows the configured default slug; it is not included as an `isDefault` response flag. Handle `role_in_use` if an attempted disable targets that default.

## Replace a role's permissions

`PUT /admin/authorization/roles/{roleID}/permissions` with `{expectedRevision,permissionKeys:[...]}` → the updated role, `200`. Requires `goauth.app.roles.update`.

This replaces the **entire** explicit set. Sending only the newly checked keys also removes all omitted keys. Send `[]` to clear; an omitted or `null` `permissionKeys` is invalid. At most 256 distinct installed, enabled keys are accepted.

A delegate must hold both the old keys and the requested keys, cannot edit its own role, and cannot customize protected roles. The example retains disabled selected keys until the operator removes them; it never silently filters an existing grant out of the draft.

### Grant editor

```tsx
// components/app-role-permissions.tsx
"use client";

import { useState, type FormEvent } from "react";
import { Button } from "@/components/ui/button";
import { Card, CardContent, CardHeader, CardTitle } from "@/components/ui/card";
import { appPermissionsApi, loadAllPermissions, reloadRole, type AppAccess, type AppRole } from "../lib/api/app-permissions";
import { getPermissionErrorMessage, permissionErrorCode } from "../lib/app-permission-errors";
import { PermissionError, PermissionKeyPicker, usePermissionQuery } from "./app-permission-ui";

export function AppRolePermissions({ role, access, onUpdated }: {
  role: AppRole; access: AppAccess; onUpdated: (role: AppRole) => void;
}) {
  const definitions = usePermissionQuery(loadAllPermissions);
  const [record, setRecord] = useState(role);
  const [keys, setKeys] = useState<string[]>(role.permissionKeys);
  const [loading, setLoading] = useState(false);
  const [stale, setStale] = useState(false);
  const [error, setError] = useState<string | null>(null);
  const unavailable = definitions.data
    ? keys.filter((key) => !definitions.data.some((permission) => permission.key === key && permission.isEnabled)) : [];
  const protectedRole = !!record.systemKey;

  async function submit(event: FormEvent<HTMLFormElement>) {
    event.preventDefault(); setLoading(true); setError(null);
    try {
      const updated = await appPermissionsApi.setRolePermissions(record.id, { expectedRevision: record.revision, permissionKeys: keys });
      setRecord(updated); setKeys(updated.permissionKeys); setStale(false); onUpdated(updated);
    } catch (error: unknown) {
      setStale(permissionErrorCode(error) === "authorization_conflict");
      setError(getPermissionErrorMessage(error));
    } finally { setLoading(false); }
  }

  async function reload() {
    setLoading(true); setError(null);
    try {
      const updated = await reloadRole(record.id);
      setRecord(updated); setKeys(updated.permissionKeys); setStale(false); onUpdated(updated);
      definitions.reload();
    } catch (error: unknown) { setError(getPermissionErrorMessage(error)); }
    finally { setLoading(false); }
  }

  return <Card>
    <CardHeader><CardTitle>Grants for {record.name} · revision {record.revision}</CardTitle></CardHeader>
    <CardContent><form onSubmit={submit} className="space-y-4">
      <PermissionError message={error ?? definitions.error} />
      {protectedRole && <p>Built-in role grants cannot be replaced.</p>}
      {definitions.loading ? <p>Loading definitions...</p> : definitions.data &&
        <PermissionKeyPicker permissions={definitions.data} selected={keys} onChange={setKeys} access={access} disabled={loading || stale || protectedRole} />}
      {unavailable.length > 0 && <div className="space-y-2">
        <p>Remove these unavailable keys before submitting:</p>
        {unavailable.map((key) => <Button key={key} type="button" variant="outline" disabled={loading || stale || protectedRole}
          onClick={() => setKeys((selected) => selected.filter((value) => value !== key))}>Remove {key} from draft</Button>)}
      </div>}
      <p className="text-sm text-muted-foreground">{keys.length} keys will replace the complete grant set. An empty set removes all grants.</p>
      <Button type="submit" disabled={loading || stale || protectedRole || definitions.loading || !!definitions.error || unavailable.length > 0 || keys.length > 256}>{loading ? "Saving..." : "Replace all grants"}</Button>
      <Button type="button" variant="outline" disabled={loading} onClick={reload}>Discard draft and reload role and definitions</Button>
    </form></CardContent>
  </Card>;
}
```

Mount with the selected role's ID/revision key. After success, replace that role snapshot everywhere, refresh access, and reload assignment selectors. A grant change advances the role revision, so an assignment form opened before the change may now conflict.

The role must be custom, unassigned, and different from the configured default. Reassign its accounts first. The server does not move them to a fallback role. A delegate must hold all existing keys and cannot delete its own role. Deleting a role does not delete its permission definitions.

## Assign an account a role

`PUT /admin/authorization/users/{id}/role` with `{roleId,expectedRoleRevision,expectedAssignmentRevision}` → `{role,assignmentRevision}`, `200`. Requires `goauth.app.roles.assign`.

Fetch the target assignment and all role choices before editing. The selected replacement must be enabled. Submitting the role's current revision prevents assigning a role whose grants changed since the operator reviewed it. The target assignment revision prevents overwriting another operator's assignment.

A delegate cannot assign itself and must hold **both the old role's keys and the new role's keys**. Transitions to or from protected admin require protected admin. The server preserves the last usable protected administrator. Assigning the existing role with valid revisions is a no-op; assignment/global revisions remain unchanged, but authorization and MFA checks still run.

### Role assignment form

```tsx
// components/assign-app-user-role.tsx
"use client";

import { useCallback, useId, useState } from "react";
import { Button } from "@/components/ui/button";
import { Card, CardContent, CardHeader, CardTitle } from "@/components/ui/card";
import { Label } from "@/components/ui/label";
import { Select, SelectContent, SelectItem, SelectTrigger, SelectValue } from "@/components/ui/select";
import { appPermissionsApi, loadAllRoles, type AppAccess, type AppUserRole } from "../lib/api/app-permissions";
import { getPermissionErrorMessage, permissionErrorCode } from "../lib/app-permission-errors";
import { hasPermission, PermissionError, usePermissionQuery } from "./app-permission-ui";

export function AssignAppUserRole({ userId, actorUserId, access, onAssigned }: {
  userId: string; actorUserId: string; access: AppAccess; onAssigned: (assignment: AppUserRole) => void;
}) {
  const load = useCallback(async () => {
    const [assignment, roles] = await Promise.all([appPermissionsApi.getUserRole(userId), loadAllRoles()]);
    return { assignment, roles };
  }, [userId]);
  const query = usePermissionQuery(load);
  const [roleId, setRoleId] = useState("");
  const [loading, setLoading] = useState(false);
  const [stale, setStale] = useState(false);
  const [error, setError] = useState<string | null>(null);
  const [result, setResult] = useState<string | null>(null);
  const id = useId();
  const selected = query.data?.roles.find((role) => role.id === roleId);
  const selfAssignment = !access.isFullAccess && userId === actorUserId;
  const oldRole = query.data?.assignment.role;
  const withinDelegation = access.isFullAccess || (!!oldRole &&
    oldRole.systemKey !== "platform_admin" && oldRole.permissionKeys.every((key) => hasPermission(access, key)));

  function reload() {
    setRoleId(""); setStale(false); setError(null); setResult(null); query.reload();
  }

  async function assign() {
    if (!selected || !query.data) return;
    setLoading(true); setError(null); setResult(null);
    try {
      const assignment = await appPermissionsApi.setUserRole(userId, {
        roleId: selected.id,
        expectedRoleRevision: selected.revision,
        expectedAssignmentRevision: query.data.assignment.assignmentRevision,
      });
      setResult(`Assigned ${assignment.role.name}; assignment revision ${assignment.assignmentRevision}.`);
      setRoleId(""); query.reload(); onAssigned(assignment);
    } catch (error: unknown) {
      setStale(permissionErrorCode(error) === "authorization_conflict");
      setError(getPermissionErrorMessage(error));
    } finally { setLoading(false); }
  }

  return <Card>
    <CardHeader><CardTitle>Assign application role</CardTitle></CardHeader>
    <CardContent className="space-y-4">
      <PermissionError message={error ?? query.error} />
      {query.loading && <p>Loading assignment and roles...</p>}
      {query.data && <>
        <p>Current: {query.data.assignment.role.name} · assignment revision {query.data.assignment.assignmentRevision}</p>
        {selfAssignment && <p>Delegated operators cannot change their own assignment.</p>}
        {!withinDelegation && <p>The current role exceeds your delegation rights; ask a protected administrator.</p>}
        <Label htmlFor={id}>Replacement role</Label>
        <Select value={roleId} onValueChange={setRoleId} disabled={loading || stale || selfAssignment || !withinDelegation}>
          <SelectTrigger id={id}><SelectValue placeholder="Choose an enabled role" /></SelectTrigger>
          <SelectContent>{query.data.roles.map((role) => {
            const canAssign = role.isEnabled && (access.isFullAccess ||
              (role.systemKey !== "platform_admin" && role.permissionKeys.every((key) => hasPermission(access, key))));
            return <SelectItem key={role.id} value={role.id} disabled={!canAssign}>{role.name} · revision {role.revision}{!role.isEnabled ? " · disabled" : ""}</SelectItem>;
          })}</SelectContent>
        </Select>
        {selected && <p className="text-sm text-muted-foreground">Review grants: {selected.systemKey === "platform_admin" ? "Protected full access" : selected.permissionKeys.join(", ") || "No explicit grants"}</p>}
      </>}
      {result && <p role="status">{result}</p>}
      <Button disabled={loading || query.loading || !query.data || !selected || stale || selfAssignment || !withinDelegation || !selected.isEnabled} onClick={assign}>{loading ? "Assigning..." : "Assign selected role"}</Button>
      <Button variant="outline" disabled={loading || query.loading} onClick={reload}>Discard selection and reload both revisions</Button>
    </CardContent>
  </Card>;
}
```

Mount with `key={userId}` when the selected account changes; `actorUserId` is your authenticated user's ID for UI feedback, not a request actor field. Selection restrictions are informational and the server rechecks everything. Use `onAssigned` to refresh the account details, role/access cards, and your own access if the operator changed its own assignment.

The result is the new role and assignment revision, not a full effective-access response. Call `getUserAccess` separately if needed. Promotion does not add MFA assurance to an existing session; administrative actions may return `two_factor_required` until the promoted account completes a new challenged login.

## Render an action with a permission check

There is no built-in browser `check-permission` endpoint. Use the top-level keys from `myAccess` to decide what to show, and call your actual business endpoint to perform the action. The backend must use `RequireAppPermission` or the equivalent service check plus your resource ownership and organization checks.

### Permission-aware business button

This example's `DELETE /posts/{postId}` is a **consumer route you implement**, not a go-auth endpoint. The backend guide shows how to guard it with `app.posts.delete`. It must share the deployment's cookie/CSRF setup; the shared wrapper supplies the header. This example also makes an access refresh available after a denial.

```tsx
// components/delete-post-button.tsx
"use client";

import { Button } from "@/components/ui/button";
```

## Put the workflow together

For a moderation workflow, use the examples in this order:

1. Protected admin initializes the installation outside the browser and signs in with required 2FA.
2. Use **Create business permission** for `app.posts.delete`.
3. Use **Create a custom role** for `moderator`, selecting that installed key.
4. Use **Assign an account a role**, selecting the returned role and submitting both observed revisions.
5. The account refreshes **Your application access**; its `permissionKeys` now includes `app.posts.delete`. Use the guarded business button and enforce it on the backend.
6. To revoke just that action, use **Replace a role's permissions**, keeping every other desired key and omitting `app.posts.delete`. To delete the definition afterward, remove it from every referencing role and use **Delete a business permission**.

For a support operator who can read accounts and revoke sessions, protected admin first installs `goauth.app.users.read` and `goauth.app.sessions.revoke`, creates a `support` role with those keys, and assigns it to the operator. The existing admin client can then call only those corresponding operations. The operator does not acquire statistics, catalog provisioning, organization oversight, or other administrative powers from its role name.

Use individual action keys to expose administrative controls. A delegated operator should not be forced through a `role === "admin"` page guard. Catalog controls require protected-admin identity; check `access.isFullAccess` for their UI visibility. Other controls use `hasPermission(access, "goauth.app.roles.create")`, and so on, while still handling runtime denials.

### Refresh and callback wiring

The callbacks in each example are part of your client application, not extra API methods. Refresh only the data a completed action can make stale:

| Completed action | Refresh |
|---|---|
| Create/edit/delete a business definition | Installed definitions and current access; grant pickers if open |
| Install library definitions | Installed definitions and grant pickers |
| Remove library definitions | Definitions, roles/revisions, open assignment selectors, current access |
| Create/edit/delete a role | Role lists/selectors and relevant access views |
| Replace/clear role grants | Role snapshot/revision, assignment selectors, current/target access |
| Assign an account | Its assignment/account details and target access; operator access if assigning itself |

Key components holding local edit drafts by record ID/revision and account panels by user ID. Reset account-scoped state when authentication changes. Do not store grants in local storage as an authorization source, manufacture revisions, auto-install library definitions from a browser effect, or silently retry a stale write.
