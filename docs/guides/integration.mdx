# Integration contract

The public Go surface separates `Auth.Services()` flows/management,
`Auth.Account(actor)` self-service, and explicit `Auth.Trusted()` primitives.
Import `github.com/nazimdjebloun/go-auth/api` for operation inputs. Mounted HTTP
routes compose internal services, authentication, cookies, CSRF and
rate limits. See the [capability inventory and API guide](./service-capabilities.mdx).

## Application HTTP routes

Use `Auth.Protect("POST /widgets/{id}", handler)` for the complete browser
protection chain on your own endpoints. Add role, app-permission or organization
wrappers inside it so they run after authentication. Patterns use ServeMux
syntax for routing, rate selection and exemptions. Put `Auth.CORS` around a
method-selecting router so preflights run before dispatch. See
[Protect application routes](./application-routes.mdx) for a full example,
failure behavior and third-party router integration.

## Actors and tenant scopes

`api.Actor` is the common user/session attribution value for business services.
It contains `UserID` and `SessionID`, with no credentials, roles, or grant cache.
`api.AppPermissionActor` is an alias, so app permission inputs accept the same
value. `actor.ForOrg(orgID)` selects a tenant and returns an
`api.OrgPermissionActor`; selection does not authorize membership or an action.

For HTTP, call `middleware.ActorFromContext(r.Context())` after `Protect` or
`RequireAuth`. It returns `(api.Actor, bool)` and rejects missing, empty, or
mismatched user/session identity. It only reads context established by trusted
backend code. Public context setters do not validate credentials.

For another backend transport, validate its raw session credential:

```go
actor, err := auth.GetActor(ctx, rawSessionToken)
if err != nil {
    return err
}
// The same actor value is accepted by app-permission inputs.
err = auth.Services().AppPermissions.RequirePermission(ctx, api.CheckAppPermissionInput{
    Actor: actor, PermissionKey: "app.reports.publish",
})
```

Check that the optional app-permission capability is enabled before using it.
`GetActor` applies `GetSession`'s current session, account and email-verification
checks. It does not refresh credentials, update activity, or establish that a
session satisfies MFA for every action. Live permission checks enforce their
current assurance policy. A custom transport must implement its own credential
delivery, rate limits, and applicable browser protections.

Organization business services can accept `api.OrgPermissionActor` from either
transport, call `AuthorizeOrg`, and pass the returned `goauth.OrgScope` to their
own repository. For example, where `InvoiceService` and `Invoice` are application
types and the repository requires a scope:

```go
func (s *InvoiceService) Get(ctx context.Context, actor api.OrgPermissionActor, id string) (*Invoice, error) {
    scope, err := s.auth.AuthorizeOrg(ctx, api.CheckOrgPermissionInput{
        Actor: actor, PermissionKey: "org.invoices.read",
    })
    if err != nil {
        return nil, err
    }
    // Every application query must include scope.OrgID as well as the record ID.
    return s.invoices.Get(ctx, scope, id)
}
```

An HTTP scoped handler supplies `scope.PermissionActor()` to that service. A
custom backend supplies `actor.ForOrg(selectedOrgID)` after `GetActor`. Both
paths use the same service check. `AuthorizeOrg` requires nonempty user and
session IDs, reloads current organization access through the permission service,
and returns a zero scope on any failure. It returns `org_permissions_disabled`
when that optional capability is off. The lower-level permission services have
their own trusted-call contracts, including conditional session requirements.

`OrgScope` includes `OrgID`, `UserID`, `SessionID`, and the resolved fixed
membership `Role`. `scope.Actor()` returns common attribution;
`scope.PermissionActor()` preserves the selected tenant and session. The role
is an informational snapshot for granular-permission applications. It cannot
authorize another operation, impersonate an owner, or bypass a subsequent check.
Active-org wrappers select the tenant from the session; explicit-org wrappers
select the path tenant. Changing the selection is independent of checking access.

These values are short-lived operation inputs, not credentials or durable access
decisions. Never construct them from client user/session IDs, even if those IDs
refer to real database rows. Recheck access in each business operation; a saved
actor/scope does not survive session expiry, grant removal, or changed assurance
as authority. The check does not cancel already authorized work or make a later
application write part of the auth transaction. Resource ownership and state
rules remain in the application service.

### Actor and scope values

`api.AppPermissionActor` aliases `api.Actor`. Scoped callbacks receive `OrgID`,
`UserID`, `SessionID` and the resolved membership role. Use keyed `OrgScope`
literals for backend test values and supply a real session ID for `AuthorizeOrg`.
Actor identity and scope fields are excluded from JSON in both directions. Use
application DTOs for client-visible IDs and keep these contracts in trusted code.

## Calling Go operations

Use `Services()` for credential/proof flows and authorized management,
`Account(actor)` for self-service, and `Trusted()` for backend primitives.
Self-service inputs omit target user/session IDs. Multi-field operations use
named input structs from `api`; single-value operations take their direct value.

```go
err := auth.Account(actor).Profile.ChangeName(ctx, name)

verified, err := auth.Services().TwoFactor.Verify(ctx, api.TwoFactorVerifyInput{
    ChallengeID:  challengeID,
    BindingToken: bindingCookie,
    Code:         code,
    IP:           clientIP,
    UserAgent:    userAgent,
})
```

Set actor IDs from authenticated server context, client metadata from the
transport, and binding/session credentials from their cookies or equivalent
trusted storage. Named inputs do not establish trust. Do not log input structs
containing passwords or one-time codes. HTTP business fields use camelCase.

OAuth callbacks supply `State` from the provider query and `BrowserState` from
the initiating browser cookie. Linking supplies the current raw session token
in `SessionToken`; the service checks those credentials and their binding.

Direct service calls do not execute HTTP middleware. Custom transports supply
authentication, authorization, rate limiting and applicable browser protections.
Check optional capabilities for nil before use. See the
[operation inventory](./service-capabilities.mdx) for each capability's contract.

## Errors across transports

Go operations return ordinary errors. Use `errors.Is` for a sentinel and `errors.As` for `*domain.AuthError`; backend errors may instead wrap their original cause. Do not send raw backend errors to clients.

Static configuration validation returns `*goauth.ConfigError`. Its `Issues`
contain stable codes and public field paths, including through `New` and
`Config.Describe` wrapping. Database/schema/custom integration startup failures
remain separate. See the [configuration error contract](../configuration.mdx#configuration-errors).

The built-in HTTP handlers and middleware use `{"error": code, "message": message}` with `Content-Type: application/json`. CSRF rejection bodies use this envelope. Match the code rather than parsing the message. OAuth callback failures remain browser redirects with an `error` query parameter. Router-generated errors and your own handlers are outside this contract. See [Error Handling](../error-handling.mdx) for codes and statuses.

## Frontend authentication outcomes

Successful HTTP authentication flows return a `step` that identifies the next
client action. OAuth callbacks use the same names in query parameters. See
[Authentication outcomes](./authentication-outcomes.mdx) for the decision table,
response fields and email-verification continuation behavior. Go service results and the HTTP error envelope have their own documented contracts.

## Authentication policy

`RegisterResult.VerificationDelivery` and `OAuthCallbackResult.VerificationDelivery`
describe the verification-email attempt independently of account creation.
Once the account exists, a failed attempt returns a verification-pending result,
not a signup error. Offer the existing resend operation; no credentials are
issued while verification is pending. `Trusted().Verify.SendVerification` and
`Account(actor).Verify.ResendVerification` return `(result, error)`. See
[delivery outcomes](./authentication-outcomes.mdx#verification-delivery-after-signup).

Password and OAuth login apply the same global and per-account email-2FA requirements. Admin OAuth also applies the admin default. Authentication and signup methods are independently selected with `WithAuthentication` and `WithRegistration`. The [policy matrix](../security.mdx#authentication-policy-matrix) specifies verification and second-factor behavior for each path.

## Optional application authorization

`WithAppPermissions(AppPermissionsConfig{Enable:true})` exposes
`Services.AppPermissions`. It is nil when disabled. Enabled mode authorizes
through the account's single `appRoleId`. Enabled-mode returned users have an
empty Go `User.Role` and omit the account `role` JSON field. Disabled mode
supports the fixed `admin` and `user` roles and returns `role` in account JSON.
Organization membership roles remain separate.

App permission operations take a trusted `api.AppPermissionActor` containing
the authenticated user ID and current session ID. Administrative
inputs use `ActorSessionID` alongside their actor/admin ID. Direct service
calls enforce the action key and required session assurance too. For stats,
use `Admin.GetStats(ctx, api.GetAdminStatsInput{ActorID: id, ActorSessionID: sessionID})`.
Supply these IDs from authenticated server context. The method checks the
operation permission and required session assurance.

Only protected administrators require local second-factor verification by
default, including OAuth login. Every other role follows the user MFA policy,
even with delegated library grants. Custom operators use ordinary login; admin
login remains reserved for protected administrators. See the
[authentication policy matrix](../security.mdx#authentication-policy-matrix).
Use `AppPermissions.RequirePermission` for backend checks and
`Auth.RequireAppPermission` after authentication on consumer HTTP routes.
Self-access responses are informational and do not authorize writes.

See [App roles and permissions](./app-permissions.mdx) for initialization,
selective library provisioning, business definitions, revisions and delegation
limits. Use the canonical schema; startup installs no permissions.

## Auth migration ownership

Auth owns its fixed tables and the `goauth_migrations` journal. Run the matching
`goauth migrate` independently of application/ORM migrations, before starting
services and workers. Keep app fields in extension tables with foreign keys;
do not include auth SQL in application desired schemas or copied host migrations.
`New` checks database connectivity and recorded migration compatibility before
starting workers, including for borrowed handles. It never executes DDL. See
[Migrations](../migrations.mdx) for adoption and recovery.

## Startup and shutdown

`NewConfig` validates configuration and starts no background work. `New` clones and revalidates it, opens or adopts the database, constructs services, and starts the configured workers. Depending on configuration, these include maintenance, recovery-email delivery, audit delivery/retention, and cleanup for the library's in-memory rate-limit stores. Create an `Auth` for the application's lifetime, rather than per request.

Inspect selected resolved settings with `cfg.Describe()` before startup or
`auth.Describe()` on a constructed instance. These data-only reports exclude
credentials and live objects and show optional capabilities, database ownership,
rate-limit storage and work enabled at startup. They are not worker-health or
connectivity checks. See [configuration inspection](../configuration.mdx#inspect-effective-configuration).

Stop accepting work and wait for HTTP requests and direct service callers to finish before calling `Auth.Close()`. `Close` does not stop or drain your HTTP server. Call it once as part of orderly application shutdown, then release resources you supplied.

| Resource | Ownership and shutdown |
|---|---|
| Database opened from `DatabaseConfig.URL` | `Auth.Close` closes it. |
| Supplied `DatabaseConfig.DB` (`*sql.DB`) | Remains open; the caller closes it after `Auth.Close`. |
| Supplied `DatabaseConfig.Pool` (`*pgxpool.Pool`) | `Auth.Close` closes its SQL adapter, leaving the caller's pool open. |
| Default route rate-limit store and internal 2FA notification store | Created and closed by go-auth. |
| Supplied rate-limit store | Remains caller-owned, including its cleanup lifecycle. |
| Supplied mailer, audit sinks, and OAuth providers | Their lifecycle remains caller-owned; `Auth.Close` does not close them. |

`Close` stops the recovery worker and maintenance before stopping audit work, then releases the owned stores and database. The audit stop receives a five-second timeout. There is no deadline for the whole `Close` call and it returns no error; custom dependencies must honor cancellation so workers can exit. A stop timeout is not a guarantee that external audit delivery finished: undelivered durable outbox records remain for later processing. If you use an asynchronous mailer, stop/drain that caller-owned mailer after `Auth.Close`.

## Browser and CSRF configuration

Configure the API origin, frontend origins and cookies through `WithBrowser`.
Use `WithSecurity` for password policy, email-link policy and pepper timestamps,
and `WithSession` for lifetimes. Challenge cookie names are configured through
`BrowserConfig.Cookies`. Keep cookie domains empty for host-only subdomain use.

Clients fetch `200 {"token":"..."}` from `/auth/csrf-token`, send credentials and
`X-CSRF-Token` on mutations, and consume replacement tokens from that response
header. The CSRF cookie is HttpOnly. Cookie helpers accept the request and return
errors: `SetSessionCookies(w, r, sessionID, sessionToken, refreshToken)`,
`ClearSessionCookies(w, r)` and `RotateCSRFToken(w, r)`. Authentication cookie
issuance includes CSRF rotation. `api.OAuthCallbackResult.SessionID` supplies the
stable session identity for custom OAuth transports.

Use `Auth.Protect` for custom browser routes. Place CORS before method routing
so preflight reaches it before authentication/rate limiting. `Auth.Mount`
registers OPTIONS for the built-in routes; applications register their own paths.

`BrowserSession` resolves `X-GoAuth-Session` before CSRF or authentication.
Keep `X-GoAuth-Session: admin` on every admin-client request, including bootstrap
and 2FA follow-ups. App and admin credentials use separate cookie contexts.
OAuth state records its initiating context; callbacks, 2FA verification and
refresh preserve that context. `Cookies.AdminName`, `AdminRefreshName` and
`AdminChallengeName` configure admin cookie names. The bundled panel selects the
context with `VITE_API_URL` pointing directly at the backend. See
[Deployment](./deployment.mdx) for HTTPS, development origins and direct API use.

## Session access checks and verification-only identity lookup

Use `Auth.GetActor` for user/session attribution, `Auth.GetSession` for full
user/session values, or `Auth.CheckSession` for a boolean credential check.
They apply the current email-verification requirement as well as session
liveness and account status. `GetActor` and `GetSession` return
`email_not_verified`; `CheckSession` returns false for a restricted account.
Credential validation does not grant a business permission.
`Auth.RequireAuth` applies the same verification requirement to custom protected
HTTP routes.

The low-level `Trusted().Session.ValidateWithUser` checks session identity and
liveness without imposing email verification. It remains available to build
verification, minimal-status and logout flows. Its successful return is not
permission to bypass verification for ordinary protected operations. The
built-in `/auth/me` exposes only minimal verification status while restricted;
`/auth/refresh` rotates cookies but similarly omits the session body.
