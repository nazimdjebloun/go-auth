# Authentication outcomes

Branch on `step` after a successful authentication response. Password login,
admin login, signup, invitation redemption and second-factor verification use
the same names. OAuth callbacks retain their redirect protocol and put `step`
in the landing URL's query parameters. Errors retain their existing HTTP
status and `{error, message}` envelope, or OAuth `error` query parameter.

| Step | Frontend action | Data |
|---|---|---|
| `authenticated` | Fetch `/auth/me`, then enter the application. | Password flows include `user` and session metadata. OAuth has already issued cookies. |
| `verify_email` | Show email verification; offer the appropriate resend operation. | Password responses include `user`. Signup includes `verificationDelivery`; OAuth verification callbacks include it in the query. Restricted `/auth/me` and refresh expose minimal status and email. |
| `two_factor` | Collect the six-digit email code and POST `/auth/2fa/verify`. | `challengeId`, `expiresAt`, `codeSent` in JSON; OAuth redirects include the ID and expiry. |
| `verify_invite_email` | Collect the invitation address-proof code and POST `/auth/oauth/invite/verify`. | OAuth callback supplies `challengeId`. The result may proceed to `two_factor`. |
| `sign_in` | Display sign-in, or repeat login using credentials still held in memory. | Returned after logout or email verification without this user's live session. |
| `linked` | Confirm the provider connection, then refresh account data. | OAuth linking keeps the existing session; it creates no new login. |

`requiresVerification`, `requiresTwoFactor`, and `requiresInviteVerification`
are removed from HTTP responses and callback queries. Replace these conditions
with comparisons against `step`. Transport-neutral Go service result structs
retain their existing fields; this change concerns the browser HTTP contract.

## Examples

```json
{
  "step": "two_factor",
  "challengeId": "...",
  "expiresAt": "2026-11-01T12:05:00Z",
  "codeSent": true,
  "message": "Two-factor code sent to your email"
}
```

The password endpoints also include `user` on this response. No session exists
for that attempt until second-factor verification succeeds. Challenge-binding
credentials stay in HttpOnly cookies and never appear in JSON or callback URLs.

```ts
type User = { id: string; email: string }
type AuthOutcome =
  | { step: "authenticated"; user?: User }
  | { step: "verify_email"; user: User; verificationDelivery?: "sent" | "not_sent" | "failed" }
  | { step: "two_factor"; challengeId: string; expiresAt: string; codeSent: boolean }
  | { step: "sign_in" }

function nextScreen(result: AuthOutcome): string {
  switch (result.step) {
    case "authenticated": return "load-current-user"
    case "verify_email": return "email-verification"
    case "two_factor": return "two-factor-code"
    case "sign_in": return "sign-in"
  }
}
```

Do not trust a landing URL as proof of authentication: anyone can edit its
query parameters. Fetch `/auth/me` with credentials; protected backend routes
remain the authority for application access. Handle an unknown step as an
integration error rather than assuming login succeeded.

## Verification delivery after signup

Account creation and verification delivery are separate outcomes. After a
password account commits, `POST /auth/register` returns `201` and
`step: "verify_email"` even if rendering, preparing, or sending the code fails:

```json
{
  "step": "verify_email",
  "user": { "id": "...", "email": "new@example.com", "isVerified": false },
  "verificationDelivery": "failed",
  "message": "Account created. Verification email could not be sent. Request a new code to continue."
}
```

| `verificationDelivery` | Meaning |
|---|---|
| `sent` | The mailer accepted the new message. This does not confirm inbox delivery. |
| `not_sent` | No new message was attempted because an existing code was reused or a cooldown applied. |
| `failed` | Preparing or sending the code failed. The account still exists and requires verification. Offer resend. |

This field is omitted when the operation did not attempt verification delivery,
including ordinary password login that only reports a verification requirement.
It is separate from `codeSent`, which continues to describe a 2FA challenge.
Transport-neutral `RegisterResult.VerificationDelivery` and
`OAuthCallbackResult.VerificationDelivery` use the constants in `api`.

OAuth callbacks for unverified identities use the same statuses in the
`verificationDelivery` query parameter alongside `step=verify_email`. New-account
creation preserves its committed provider link when delivery fails, so a fresh
OAuth attempt resumes the same identity. Invalid OAuth state, provider errors,
and failures before account creation retain the usual error behavior.

Keep the user on the verification screen and show a resend action instead of
inviting them to create the same account again. Use
`POST /auth/verify-email/resend` with the email address. It queues a durable public
recovery request and returns the same generic response for existing and absent
accounts; it does not expose delivery status. Token reuse, cooldowns, attempt
limits and worker retry policy remain in effect. Initial signup delivery is a
synchronous attempt; `failed` does not mean a background retry was queued.

Email verification continues to create no credentials. No password signup or
OAuth verification-pending outcome bypasses verification or MFA. Invitation
redemption already establishes email ownership and has no separate account
verification-email step. MFA challenge delivery and session-issuance errors are
outside this delivery-status contract and retain their existing behavior.

## Email verification and existing sessions

`POST /auth/verify-email` never creates credentials. It returns `authenticated`
when the selected context already has a live, non-banned session belonging to
the account just verified; that same session can resume application access.
It returns `sign_in` otherwise. A different account's cookie does not qualify.
If optional session lookup fails because the database is unavailable, the
request fails before consuming the one-time verification code.

`GET /auth/me` remains a profile endpoint: its normal profile shape gains
`step: "authenticated"`. When verification is pending, it returns only `id`,
`email`, `isVerified: false`, and `step: "verify_email"`. Refresh similarly
returns the step and either session metadata or minimal pending status.
Public resend responses remain generic and do not reveal whether an account
exists. Session refresh, CSRF rotation and challenge binding keep their existing
cookie behavior.

Admin clients send `X-GoAuth-Session: admin` throughout this flow, including
verification, resend, CSRF bootstrap, refresh and logout. App clients use the
app context. Both may call one API host while keeping independent sessions.
