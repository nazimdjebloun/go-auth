# Routes

This page covers every route `Auth.Mount(mux)` registers. Paths in the tables use `{name}` for a path parameter read via `r.PathValue("name")`. "Auth" is the minimum session/role required — see [Architecture](architecture.mdx#the-middleware-chain) for the full middleware chain each route runs through, and [Error Handling](error-handling.mdx) for what each one returns on failure.

A few routes are conditionally mounted and simply don't exist on the mux otherwise:

- Everything under **Invites** requires `RegistrationConfig.EnableInvite: true`.
- Everything under **OAuth** requires `RegistrationConfig.EnableOAuth: true` and at least one `WithProvider` call.
- Everything under **Organizations** requires `WithOrganizations(OrganizationConfig{Enable: true})`.
- `POST /auth/register` requires `RegistrationConfig.EnableEmailPassword: true`.

Whenever `SecurityConfig.AllowedOrigins` is non-empty, Mount also registers an `OPTIONS` twin for every distinct path (deduplicated across methods sharing one), short-circuited to `204` by the CORS middleware before reaching any handler — these aren't listed separately below.

|---|---|---|---|
| `POST /auth/register` | Public | `` `{email, password, name}` `` | Register with email/password. Returns a session unless verification is required, or `RequireEmail2FA` is on (see [Two-factor authentication](#two-factor-authentication)). |
| `POST /auth/login` | Public | `` `{email, password}` `` | Log in. May return `requiresVerification: true` instead of a session, or `requiresTwoFactor: true` if the account has 2FA on. |
| `POST /auth/admin/login` | Public | `` `{email, password}` `` | Same as login, but only succeeds for `role: admin` users. Requires a second factor unless `SecurityConfig.DisableAdminTwoFactor` is set — see [Two-factor authentication](#two-factor-authentication). |
| `POST /auth/logout` | Auth | none | Revokes the current session and clears its session + refresh cookies. |
| `GET /auth/me` | Auth | none | Returns the authenticated user plus `hasPassword`. |
| `GET /auth/check` | Public (session cookie optional) | none | Soft check — always `200`, returns `{"user": null}` instead of erroring when there's no valid session. |
| `GET /auth/csrf-token` | Public | none | No-op handler (`204`) — the CSRF cookie/header is actually issued by the CSRF middleware wrapping this route. Call it to prime the cookie before your first mutating request. |
| `PUT /auth/name` | Auth | `` `{name}` `` | Updates the authenticated user's display name. |

## Two-factor authentication

`Login`, `AdminLogin`, `Register`, and `POST /auth/invite/register` all return the same gated shape when a second factor is still owed: `{user, requiresTwoFactor: true, codeSent, challengeId, expiresAt, message}` — no session/refresh cookie, no CSRF rotation. Alongside that body, the response sets a binding cookie (name from `SecurityConfig.TwoFactorChallengeCookieName`, default `_2fa_challenge`; HttpOnly; same `Domain`/`Path`/`Secure`/`SameSite` as the session cookie; `MaxAge` = `TwoFactorCodeTTL`) that ties the challenge to the browser that started it. `POST /auth/2fa/verify` and `POST /auth/2fa/resend` both require that cookie back — a `challengeId` alone (e.g. one that leaked into a log line) is not a usable credential without it. The cookie is skipped entirely when `SecurityConfig.DisableTwoFactorChallengeBinding` is set, for non-browser consumers.

| Method & Path | Auth | Body | Description |
|---|---|---|---|
| `POST /auth/2fa/verify` | Public (requires the binding cookie, unless disabled) | `` `{challengeId, code}` `` | Completes any of the four gated flows above. Sets session+refresh cookies and clears the binding cookie on success. Wrong code, wrong binding cookie, and a capped lineage (5 wrong guesses) all return the same `two_factor_code_invalid` — see [Error Handling](error-handling.mdx). |
| `POST /auth/2fa/resend` | Public (requires the binding cookie, unless disabled) | `` `{challengeId}` `` | Refreshes the code on the same challenge — the `challengeId` doesn't change. Capped at 3 resends per challenge; an unknown or binding-mismatched challenge gets the same generic `200` as a real send, to avoid enumeration. |
| `POST /auth/2fa/enable` | Auth | `` `{password, keepOtherSessions}` `` | Turns on per-user 2FA after re-checking the password. `keepOtherSessions` defaults to `false` (omitted = revoke every other session) — spelled this way so the zero value is the safe one, matching `DisableCSRFToken`. Rejected with `two_factor_already_enforced` if `RequireEmail2FA` is on. |
| `POST /auth/2fa/disable` | Auth | `` `{password}` `` | Turns off per-user 2FA after re-checking the password. No session revocation — turning 2FA off isn't the "someone may be in my account" signal that turning it on is. Rejected with `two_factor_already_enforced` if `RequireEmail2FA` is on. |

### Invite status and expiry

`expired` is derived, not stored. The terminal status is only written when
someone opens an invite link, so an invite that simply lapsed still sits in the
table as `pending`. `GET /admin/invites` closes that gap in both directions:

- `status=pending` matches only invites that are still valid.
- `status=expired` matches invites already written as expired **and** pending
  invites past `expires_at`.
- Rows are returned with the derived value, so a lapsed invite reads
  `status: "expired"` even though the stored column says `pending`.

The redemption endpoints are unaffected — they distinguish revoked from expired
themselves and write the terminal status.

### Bulk invite responses

Every bulk invite endpoint returns `{succeeded: string[], failed: [...]}` and is
**not** transactional, so both lists must be read. Failures carry `inviteId` for
the ID-keyed actions and `email` for `bulk/send`, where no invite exists yet.

`bulk/send` and `bulk/resend` cap at 25 per request rather than 100: each item
is an SMTP round-trip, dispatched across a small worker pool. Chunk larger
lists client-side.
